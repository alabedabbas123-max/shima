# الهيكل الهندسي وحدود التنفيذ

## الطبقات

```text
التطبيق المضيف
  ├─ EditText أو EditorAdapter (main thread)
  └─ CodeAnalyzer / AnalysisHandle
       ├─ Handler debounce + نسخ النص مرة بعد فترة الهدوء
       ├─ عامل واحد، وصف انتظار بحد عنصر واحد، وإلغاء تعاوني + generation
       └─ Analyzer (Java مستقل عن Android UI)
            ├─ LRU: هوية ملف + اللغة + النص السابق + شجرة/أحداث
            ├─ Tree-sitter Java / Kotlin (C + JNI)
            │    └─ شجرة معدلة بـTSInputEdit ثم parse تزايدي
            ├─ فهرس أسماء المشروع والموارد + SAX XML
            ├─ قواعد Java وAndroid محدودة مبنية على عقد AST
            └─ Diagnostic / SourceRange / QuickFix / WorkspaceFix
  ├─ dependencies: ماسح Gradle وMaven مقيد وكاش محروس
  └─ ui اختياري: خطوط متعرجة وToast وقائمة إصلاح ونافذة تقدم
```

الواجهات العامة في `analyzer/src/main/java/com/shima/analyzer/{core,editor}`؛ التنفيذ الأصلي في `native_bridge.c`. لا تعتمد طبقة `core` على `Context` أو `View`، مع أن JNI مطلوب عند تنفيذ الفحص. يمكن اختبارها في JVM على Linux ببناء `.so` للمضيف بواسطة `scripts/test-host.sh`. يمكن للمضيف الرسم بنفسه أو استخدام أدوات `ui` الاختيارية؛ SDK لا يغير النص إلا عند استدعاء `applyFix` صراحة، ولا يكتب إصلاحات workspace على القرص.

## سير الطلب

1. يرسل الـadapter إشعار التغيير على main thread. تُلغى مهمة الانتظار والطلب السابق، ويزيد رقم الجيل فوراً.
2. بعد 250ms افتراضياً تُؤخذ لقطة `String` من المحرر على main thread. يمررها عامل واحد إلى المحرك. لا تؤخذ نسخة كاملة عند كل ضغطة، بل بعد debounce؛ النص الضخم ما زال يتطلب ذاكرة لدى المحرر واللقطة.
3. عند توفر شجرة سابقة يقارن المحرك البادئة واللاحقة المشتركتين، مع مراعاة أزواج UTF-16 surrogate، ويهيئ `TSInputEdit` بإحداثيات الأسطر والأعمدة. تُنسخ الشجرة السابقة بنسخة Tree-sitter تشاركية، وتُعدّل النسخة قبل إعادة التحليل. إذا أُلغي التحليل لا تفسد الشجرة السابقة؛ وعند سباق الإلغاء مع اعتماد النتيجة تُستبعد حالة الملف بالكامل لضمان عدم تطبيق تعديل على لقطة خاطئة.
4. يقرأ المحرك عقد الأخطاء والأنواع والحزم والاستيرادات وبعض التهيئات والاستدعاءات. يضع حدوداً لعدد العقد والأحداث والتشخيصات، ويعطي تحذير `PARTIAL` عند الاقتطاع. قواعد الدلالة لا تعمل في ملف تظهر فيه أخطاء syntax.
5. تعود النتيجة إلى main thread فقط إن كان رقم الجيل ما زال حديثاً والجلسة مفتوحة. الإلغاء يستخدم رقم جيل ذرياً داخل callback للمحلل؛ إذا كان المحلل داخل عمل لا يستدعي callback فقد يتأخر التوقف، فلا توجد مهلة زمن حقيقية صارمة.
6. `close()` يفصل الـlistener ويزيل callbacks ويوقف الطلبات، ثم يحرر شجرات JNI على العامل بعد خروج الفحص الحالي. `Analyzer.close()` المتزامن قد ينتظر فحصاً جارياً، لذا لا تستدعه مباشرة من واجهة المستخدم أثناء الفحص.

تعالج الشجرة الملف كاملاً عند أول فحص، وتعيد استخدام أجزاء عند التعديل. **ليس** هذا تحليلاً دلالياً تزايدياً كاملاً ولا ضماناً لإعادة فحص سطر واحد فقط؛ أي تعديل قد يغيّر سياق أسطر أخرى.

## المشروعات والتخزين

`analyzeProject` يقبل لقطات الملفات من المضيف على مرحلتين: تحليل الملفات وجمع أسماء الأنواع العليا، ثم بناء فهرس وإعادة القواعد التي تعتمد عليه لكل ملف. إعادة تحليل لقطة غير متغيرة تستعمل أحداث الشجرة المخزنة إذا لم تخرج من LRU، لكن نتائج الاستيراد لا تُخزن مستقلة عن فهرس المشروع؛ لذلك تغييرات الإضافة والحذف والحزمة لا تعيد اقتراحات قديمة. حذف ملف من قائمة المشروع يزيل حالته المخزنة. لا يوجد رسم اعتماديات أو classpath resolution، وبالتالي لا يمكن الاقتصار على إعادة فحص المعالين دلالياً فقط. إذا كان فهرس المشروع ناقصاً بسبب حد أو خطأ syntax، تُحجب اقتراحات الاستيراد وتعاد حالة جزئية.

`analyzeWorkspace` يضيف موارد `ResourceFile` وXML إلى اللقطات التي يقدمها المضيف. يُعاد استخدام فهرس الموارد إذا بقيت اللقطات والعلم متطابقين، وتُعاد القواعد الدلالية لكل طلب. موارد ناقصة تحجب تشخيص الغياب وتظهر `RESOURCE_INDEX_INCOMPLETE` عند وجود مرجع ذي صلة؛ إصلاح الملفات المتعددة يقارن بصمات المصدر والهدف ويحتاج transaction من المضيف. حدود Maven ودورة الواجهة وأمثلة كل ميزة في [دليل الميزات الثماني](ADVANCED_FEATURES.ar.md).

الإعدادات الافتراضية عبر `AnalysisConfig.builder()`:

| المورد | الحد الافتراضي | المعنى |
|---|---:|---|
| الملف | 200,000 | وحدة UTF-16 |
| المشروع | 2,000,000 / 500 | وحدات UTF-16 / ملفات في اللقطة |
| LRU | 8 | أشجار ملفات أصلية كحد أعلى لكل `Analyzer` |
| الأحداث | 12,000 | أحداث AST لكل ملف |
| العقد | 250,000 | حد داخلي ثابت لاجتياز الشجرة لكل ملف |
| التشخيصات | 100 | لكل نتيجة؛ تجاوزها يعطي `PARTIAL` |
| المهلة | 1,000ms | ميزانية تعاونية للتحليل واجتياز الشجرة، لا حد قاطع للجدار الزمني |
| Android | minApi 21، compileApi 35 | يمكن ضبطهما، وليس كتالوجاً شاملاً |
| أنواع المضيف وبيانات API | 50,000 نوع مضيف، و50,000 مدخل API إضافي | حدود مستقلة لكل إعداد؛ يمكن أن تستهلك ذاكرة ملحوظة |

يمكن ضبط الحدود من `AnalysisConfig` ضمن نطاقاتها المعلنة. تُحفظ الأشجار والأحداث والنصوص السابقة لعدد محدود من الملفات؛ يزيد استخدامها أو عدد جلسات المحرر من الذاكرة. واجهة المشروع تحتفظ أيضاً بنتائج وأحداث مؤقتة أثناء الطلب، والمضيف يملك لقطاته. الحدود لا تضمن عدم التسرب إن لم يحرر المضيف الجلسة، ولا تضمن استحالة OOM؛ تخصيصات Tree-sitter الأصلية قد تستدعي `abort()` عند فشل تخصيص الذاكرة. اختبر على أجهزة حقيقية وأحجامك قبل الإنتاج.

## التشخيصات والإصلاحات

| الكود | الوصف |
|---|---|
| `SYNTAX_ERROR`, `MISSING_TOKEN` | عقد `ERROR`/العناصر الناقصة في القواعد، وقد يتوفر إدراج رمز واضح |
| `POSSIBLE_MISSING_IMPORT` | اسم نوع معروف غير محلول بحسب الفهرس المتاح؛ اقتراح، وليس دليلاً على خطأ مترجم |
| `INCOMPATIBLE_LITERAL` | تعارض واضح في تهيئة حرفية مباشرة مع نوع بدائي/`String` محدود |
| `ANDROID_API_LEVEL`, `ANDROID_DEPRECATED` | مطابقة مالك/اسم مدرج في الكتالوج الصغير أدناه |
| `MISSING_RESOURCE`, `RESOURCE_INDEX_INCOMPLETE` | غياب مؤكد نسبةً للقطات كاملة فقط، أو فهرس موارد غير مكتمل |
| `MISSING_ABSTRACT_METHODS`, `MISSING_OVERRIDE_ANNOTATION` | subset خاص بـJava BaseAdapter؛ الثاني سياسة اختيارية لا syntax |
| `DUPLICATE_FIELD`, `DUPLICATE_METHOD`, `UNRESOLVED_METHOD` | فحوص Java محافظة لأعضاء الصنف واستدعاءات محددة |
| `UNUSED_FIELD`, `UNUSED_METHOD`, `UNUSED_LOCAL`, `UNUSED_CLASS` | تحذيرات Java محدودة وقد تتأثر بالانعكاس |
| `XML_SYNTAX_ERROR`, `XML_INVALID_DIMENSION`, `XML_DTD_FORBIDDEN` | XML/قيم layout محدودة ورفض DTD |
| `DOCUMENT_TOO_LARGE`, `ANALYSIS_TIMEOUT`, `ANALYSIS_LIMIT`, `PARSER_FAILURE`, `PARSER_UNAVAILABLE`, `PROJECT_INDEX_INCOMPLETE` | النتيجة غير مكتملة |

تُرتّب التعديلات تنازلياً بحسب موضعها وتطبق على نفس لقطة UTF-16. تُحسب SHA-256 على وحدات UTF-16 نفسها بما فيها المحارف البديلة غير المزدوجة؛ وتُرفض أي نسخة تغيرت. قد يكون اقتراح الاستيراد غير مناسب بسبب حدود الفهرس/الرؤية؛ لا يطبّق تلقائياً، وتُعرض أول ثمانية إصلاحات كحد أقصى لكل تشخيص. مع shebang أو `@file:` في Kotlin وغياب package/import لا يُقترح إدراج استيراد آلي لتجنب وضعه قبل الترويسة.

## كتالوج Android المضمن

هذه البيانات محددة يدوياً وقُورنت ببيانات API الموجودة في المستودع؛ ليست قاعدة كل Android API أو كل إصدارات Android المستقبلية:

| رمز | منذ API | deprecated منذ |
|---|---:|---:|
| `android.app.NotificationChannel` | 26 | — |
| `android.os.LocaleList` | 24 | — |
| `android.os.VibrationEffect` | 26 | — |
| `android.hardware.biometrics.BiometricPrompt` | 28 | — |
| `android.app.Person` | 28 | — |
| `android.content.pm.ShortcutInfo` | 25 | — |
| `android.app.role.RoleManager` | 29 | — |
| `android.view.WindowInsetsController` | 30 | — |
| `android.app.ProgressDialog` | 1 | 26 |
| `android.os.Trace.beginAsyncSection/endAsyncSection/setCounter` | 29 | — |
| `android.provider.Settings.canDrawOverlays` | 23 | — |
| `android.os.Build.getSerial` | 26 | — |

الفحص يطابق الأنواع وبعض الاستدعاءات الساكنة ذات المالك المعروف فقط. `minApi` يقبل 21 وما فوق إذا كان `compileApi >= minApi`، لكن لا يعني قبول الرقم تغطية APIs جديدة. لا يتتبع guards مثل `SDK_INT` و`@RequiresApi` أو overloads/الوراثة/المستقبلات المتغيرة؛ لذا التحذير يطلب التحقق من الحماية ولا يجزم بالخطأ. الرمز غير الموجود بالكتالوج لا ينتج تحذيراً ولا يعني أنه متوافق. لا يعمل `compileApi` كتحقق من أن الرمز موجود فعلاً في SDK الذي جرى البناء به.

### إضافة بيانات API من المضيف

يمكن تزويد فئات `android.*` وطرقها الساكنة ببيانات دقيقة من مصدر مرخّص ومحدّث يختاره المضيف، مثلاً:

```java
AnalysisConfig config = AnalysisConfig.builder()
        .minApi(21).compileApi(35)
        .addAndroidApiType("android.graphics.RenderNode", 29, 0)
        .addAndroidApiStaticMethod("android.os.Trace", "isEnabled", 29, 0)
        .build();
```

الرقم الأخير `0` يعني عدم تقديم نسخة إهمال؛ وإلا فليكن رقم API الذي بدأ فيه الإهمال، ولا يقل عن `sinceApi`. نوع API المضاف يدخل أيضاً في قائمة مرشحي الاستيراد؛ إضافة method وحدها لا تضيف مالكها للفهرس. المدخلات المخصصة **تتجاوز** القيم المضمنة ذات المفتاح نفسه، وتنسخ عند `build()`، لذلك يتحمل المضيف مسؤولية صحتها. الفحص يطابق اسم الطريقة لا توقيع الـoverload ولا يحلل methods على الكائنات أو الحقول أو guards. لا يوجد تحديث آلي أو قاعدة شاملة؛ لا تسد هذه الواجهة النقص إلا في الرموز التي يزودها المضيف بالفعل.

## النطاق والقيود

- Tree-sitter محلل syntax متسامح مع الأخطاء، وليس Java/Kotlin compiler؛ قد تفوته أخطاء نحوية أو يعدّ بعض تركيبات اللغة الحديثة غير مدعومة. في قواعد Kotlin المثبتة تُتجاهل عقد `MISSING` الداخلية التي يبدأ اسمها بـ`_` لتقليل إنذارات الفواصل الاصطناعية، وهذا قد يخفي بعض الأخطاء أيضاً.
- لا يوجد فحص كامل للأنواع، overload resolution، nullability، تدفق البيانات، رموز المتغيرات المفقودة، الوصول أو الوراثة، مكتبات Gradle، Java annotation processing أو مشروع متعدد الوحدات. قواعد BaseAdapter وstubs والاستعمالات والتكرار محدودة ولا تستبدل مترجماً. الأسماء المؤهلة المزودة من المضيف تُستخدم للاقتراحات ولا يثبت وجودها أو قابلية الوصول إليها.
- لا يُحلّل classpath أو JARs أو ملفات Android SDK تلقائياً؛ الاقتراحات لا تشمل كل الاستيرادات، ويمكن أن تقترح نوعاً غير متاح/غير مرئي. الكود غير المعروف لا يولّد خطأ اسم غير معرّف.
- جدول Android محدود كما هو مبيّن؛ لا توجد تغطية كاملة من API 21 إلى أحدث إصدار، أو معرفة كل deprecated methods، أو تحليل runtime guards. عدم وجود تحذير ليس ضمان توافق.
- لا أرقام benchmark على أجهزة Android هنا ولا ادعاء تفوق/تكافؤ أداء مع AIDE. يجب قياس حجم AAR وأداء كل ABI واستهلاك الذاكرة واختبار دورة الحياة على أجهزة API 21 والإصدارات الحديثة.
- لتوسعة إنتاجية كاملة يلزم مصدر مفهرس ومرخّص لبيانات SDK محدث حسب الإصدارات والتواقيع، وحل classpath وبنية المشروع، ومحركي دلالة Java/Kotlin مع اختبارات توافق ومقارنات على أجهزة فعلية. هذه أعمال مستقبلية وليست مضمّنة.

المصدر الجديد لم يُضف له ترخيص مشروع عام في هذا المستودع؛ يقرر المالك ترخيصه. تراخيص Tree-sitter المستعملة مُدرجة في ملف الإشعارات المهيأ للتضمين في الـAAR.

## التحقق المنفذ وحدوده

- على Linux x86_64 نجحت **344 فحصاً** في `scripts/test-host.sh` باستخدام محللي JNI الحقيقيين وبدائل اختبار لواجهة Android، من بينها فهرسة Java/Kotlin، والإلغاء، وتغيرات UTF-16، وإصلاحات قديمة، وتوسعة كتالوج API. العدد نتيجة التشغيل الحالي، وليس معيار تغطية أو benchmark.
- جُمعت مصادر Java وإصلاحات مولدة نموذجية ضد نسخة خارجية من stubs الخاصة بـAndroid API 21 عبر `scripts/check-api21.sh` و`scripts/test-generated-fixes.sh`؛ هذا يفحص توفر واجهات Java/Android المستخدمة فقط ولا يشغّل المكتبة على جهاز. نسخة jar المستخدمة للاختبار من [Sable/android-platforms](https://github.com/Sable/android-platforms/blob/master/android-21/android.jar)، وبصمتها SHA-256: `91a151cc33ce2359019c23f075f99bee6857f81506ce302a4e019f00489f7105`. يستحسن للمستخدم التحقق أيضاً بنسخة SDK الرسمية على جهازه.
- **لم يُبنَ AAR هنا ولم تُشغّل اختبارات Android**: بيئة التنفيذ لا تحتوي SDK/NDK ولا تسمح بتنزيل Gradle من `services.gradle.org`؛ توقفت المحاولة عند تنزيل التوزيعة قبل بناء Android. لم يُقَس حجم AAR أو سرعة أجهزة Android، ولم تُتحقق بنية المعماريات أو تطبيق `sample` بعملية بناء فعلية. ملفات Gradle وCI والاختبارات مهيأة، لكنها ليست دليلاً على نجاح البناء حتى تُشغّل في بيئة Android كاملة.
