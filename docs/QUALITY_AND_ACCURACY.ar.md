# دقة الفحص والحدود والتشخيصات المعلّقة

**التاريخ:** 31 أكتوبر 2026

هذا التقرير يصف تعديل SDK وربطه في نسخة `sh129.zip` المحددة، لا يثبت ما يعمل في APK المثبّت لديك. خطوات دمج التطبيق في [دليل تصحيح sh129](../integrations/sh129/QUALITY.ar.md)، وخطوات بناء AAR والميزات الثماني في [تقرير SDK](SDK_REPORT.ar.md) و[دليل الميزات](ADVANCED_FEATURES.ar.md).

## إعادة الإنتاج والسبب

أنشأنا على Linux اختباراً مصغّراً يستخدم JNI الحقيقي وربط `sh129`: **70 ملف XML** احتوت مراجع موارد، مع إعلان فهرس الموارد غير مكتمل. أعاد المحرك 70 نتيجة `PARTIAL` بسبب نقص الفهرس، لكن الربط القديم وصفها جميعاً خطأً كأنها حد وقت أو حجم، ثم احتفظ بنتائج **64 ملفاً فقط** بسبب سياسة إخلاء. هذه إعادة إنتاج للسلوك، وليست إثباتاً أن ملفات مشروعك أو عدد التحذيرات في جهازك متطابقان معها. لم نحلل APK المثبت أو مشروعك الجاري فحصه.

## ما تغيّر

| المشكلة | التعديل | الحد المتبقي |
|---|---|---|
| رسالة جزئية متكررة وغير دقيقة | `AnalysisResult.getIncompleteReasons()` يسجل أسباباً مستقلة مثل `RESOURCE_INDEX_INCOMPLETE` و`PROJECT_INDEX_INCOMPLETE` و`DIAGNOSTIC_LIMIT` أو أسباب المحلل. في ربط sh129 تُجمع فجوات التغطية برسالة واحدة بدلاً من اعتبار كل ملف تجاوز مهلة. إذا اجتمعت أسباب فلا يُمحى بعضها. | وجود `PARTIAL` ما زال يعني أن هناك فحوصاً لم تكتمل؛ لا ينبغي إخفاء الحالة أو اعتبار النتيجة سليمة. قد تظهر أسباب أخرى مثل تلف XML أو DTD مرفوض. |
| ضياع نتائج ما بعد 64 ملفاً | الجسر يجمع نتيجة جيل الفحص على عامل، ثم ينشرها على main thread بعد اكتمال ذلك الجيل؛ أُزيل إخلاء 64 ملفاً. | سقف **25,000** صف جديد لكل جيل: تعرض رسالة جزئية عند بلوغه. قد تُضاف صفوف سابقة معلقة ضمن سقف كل ملف، ويبقى حد التشخيصات لكل ملف. |
| حدود 400 ملف و1,500,000 حرف تقتطع بقية المشروع | مخطط التطبيق ينشئ دفعات ويواصل الملفات، ويبلغ عن الملفات الكبيرة وغير المقروءة والمجلدات التي تعذر مسحها؛ يمنع روابط خارج الجذر وحلقات المجلدات. مورد ثنائي مثل PNG يفهرس اسمه ولا يحلل كنص؛ Manifest يُفحص كـXML. | الدفعات ليست فهرس مشروع موحداً: تُعطّل الأحكام المبنية على غياب مصدر عبر دفعات منفصلة، وتُعلن الجزئية. موارد المكتبات وvariants وAAPT2 لا تدمج تلقائياً، وقد يحتوي المشروع الكبير على حدود أخرى. |
| اختفاء علامة الخطأ بعد أي تعديل | يبقي `DiagnosticTracker` و`EditTextSquiggles` وعرض sh129 العلامات السابقة بوصفها **معلّقة**، مع إزاحات تقريبية، إلى أن تُنشر نتيجة أحدث للملف/الجيل. أي تعديل، حتى داخل النطاق، لا يثبت الإصلاح. | موضع العلامة أثناء الانتظار تقريبي، وليس إثباتاً أن الخطأ الحالي ما زال موجوداً. لا يجوز تطبيق إصلاح من نتيجة معلّقة؛ البصمة تمنع أيضاً تطبيق إصلاح على نص مختلف. غياب التحليل الجديد يترك العلامة معلّقة بدلاً من إخفائها. |
| نتائج قديمة أو بعد إغلاق المشروع | يلغى الجيل القديم تعاونياً، وتُحرس نتائج العامل والـcallbacks بأجيال المشروع والنص؛ يُغلق المحرك عند إنهاء النشاط. تستمر حماية التركيز السابقة. | المهلة والإلغاء تعاونيان وليسا ضمان حد زمني صارم، ودورة الحياة لم تُختبر على Android. |
| تحذيرات unused تحجب الأخطاء | unused يبقى `WARNING` أصفر ويُستبعد من لوحة الأخطاء الحرجة في sh129. عند ازدحام قائمة تشخيصات workspace المحدودة تحتفظ القائمة بالأخطاء قبل التحذيرات، وتبلغ `DIAGNOSTIC_LIMIT` إذا اقتطعت. | فحوص unused محافظة وقد تتأثر بالانعكاس والموارد؛ قائمة محدودة قد تحذف بعض النتائج ذات الأولوية نفسها. |
| إعادة عمل XML غير متغير | يعيد المحرك استخدام نتائج XML المكتملة التي لم يتغير مسارها أو نصها، ويعيد المحاولة للنتائج الجزئية؛ يعيد بناء فهرس الموارد عند التغير. | تُعاد بعض قواعد المشروع دلالياً، ولا توجد بنية اعتماديات دلالية كاملة. في ربط sh129 يُعاد استخدام المحرك بين الفحوص ذات الإعداد والدفعة الواحدة؛ المشاريع متعددة الدفعات ليست cache دلالياً موحداً. |
| افتراض إصدارات أو مكتبات غير المشروع | إعداد إصدار المشروع الافتراضي `minApi=0` و`compileApi=0` يعني مجهول، ويقبل إصدار مشروع أقل من 21؛ أما **تشغيل SDK نفسه** فما زال يتطلب API 21. ربط sh129 لا يستبدل القيمة المجهولة بإصدار الجهاز، ويقبل الأرقام الحرفية المعروفة فقط من إعداد المشروع. `ClasspathSymbols` يفهرس الأصناف العامة العليا من JAR/AAR محددة لمرشحي imports. | لا تُحل تعبيرات Gradle وversion catalogs وvariants وPOM/classpath الكامل تلقائياً، ولا تفحص الفهرسة أعضاء المكتبات أو توفرها في variant. Android API المضمن عينة صغيرة ولا يحلل guards أو كل signatures. إذا كانت الإعدادات مجهولة فغياب تحذير لا يثبت التوافق. |

## دقة أعضاء Java وأنواع الملفات

يتتبع SDK أنواع المستقبلات المحلية والحقول والوراثة **عندما يكون مصدر النوع وسلسلة آبائه معروفين على نحو موثوق**. كُشفت في اختبار الربط `this.clibs.getKay()` و`setKay(...)` وحقل مفقود، ولم يُنفَ عضو قد يكون موجوداً في أب خارجي غير مفهرس. هذا فحص اسم العضو فقط، وليس فحص توقيع أو توافق معاملات أو رؤية كل عضو مكتبة. على مسار التطبيق القديم حُجب الحكم على الحقول والدوال والأنواع عند غموض الوراثة أو الاعتماديات؛ وأُوقفت قواعد imports التي تفحص النص الخام لأنها قد تخطئ في التعليقات والنصوص. لذلك تنخفض التغطية عندما ينقص اليقين.

الطلب بفحص كل أنواع الملفات وكل الملفات الكبيرة **لم يتحقق بالكامل**: SDK يدعم Java/Kotlin/XML فقط، ومسار التطبيق القديم لديه Smali أيضاً، لكنه لا يُحلّل Groovy/Gradle أو HTML أو النصوص الأخرى تحليلاً شاملاً. حد ربط workspace هو 200,000 وحدة UTF-16 لكل ملف، ويُعلن نقص التغطية بدل اعتبار ما تُرك سليماً. DTD مرفوض. Unicode escapes الآمنة داخل نصوص/تعليقات مختارة لا توقف الفحص، لكن التهريبات التي قد تغير حدود الرموز تعطي `JAVA_UNICODE_ESCAPES_UNSUPPORTED` و`PARTIAL`؛ ليست معالجة Java Unicode المسبقة مكتملة.

قناة التطبيق القديمة تستعمل الخدمة المعلنة `:analyzer`، بينما SDK وربط المشروع يعملان على عمال خلفيين؛ هذا ليس إثباتاً لعزل كامل عن جميع خدمات التطبيق أو لعدم تجمده على جهاز. تقسيم النقل إلى 48,000 وحدة يحافظ على أزواج surrogate، ورفض الطلبات والردود القديمة مرتبط بالجيل والملف؛ فُحص ذلك بمحاكيات JVM لا Binder حقيقي.

## استعمال أسباب الجزئية والمحرر المخصص

عند بناء `WorkspaceSnapshot` يجب على المضيف تمرير كل اللقطات التي يزعم اكتمالها. `projectIndexComplete` افتراضياً `true`، لذلك اضبطه `false` عند إرسال جزء من المصادر أو تعذر المسح؛ و`resourceIndexComplete` افتراضياً `false` ويجب ألا يصبح `true` إلا عند توفير الموارد اللازمة بما فيها الاعتماديات والـvariant المقصود. إذا احتوت المصادر أخطاء syntax أو فشل تحليلها يصبح فهرس المشروع ناقصاً تلقائياً لبعض القواعد. لا ترفع الحدود فقط لإخفاء الجزئية.

```java
WorkspaceSnapshot snapshot = WorkspaceSnapshot.builder()
    .projectIndexComplete(allProjectSourcesIncluded)
    .resourceIndexComplete(allMergedResourcesIncluded)
    // .addSource(...) و .addResource(...) لكل لقطة مناسبة
    .build();
WorkspaceResult workspace = engine.analyzeWorkspace(snapshot); // عامل خلفي
// كرر المعالجة على workspace.getResources().values() لنتائج XML أيضاً.
for (AnalysisResult result : workspace.getSources().values()) {
    if (result.getStatus() == AnalysisResult.Status.PARTIAL) {
        for (String reason : result.getIncompleteReasons()) {
            // ميّز RESOURCE_INDEX_INCOMPLETE عن ANALYSIS_LIMIT وغيرها في واجهتك.
        }
    }
}
```

لمحرر مخصص، طبق `DiagnosticTracker` على الخيط الذي يملكه المحرر، ومرر كل تغيير بإحداثيات UTF-16؛ انشر نتيجة المحلل فقط إذا كانت تخص النسخة الحالية:

```java
DiagnosticTracker tracker = new DiagnosticTracker();
// عند وصول نتيجة حديثة مؤكدة للنسخة الحالية:
tracker.setCurrent(result.getDiagnostics());
// لكل استبدال [start, start + removed) في النص:
tracker.applyEdit(start, removed, inserted, currentTextLength);
for (DiagnosticTracker.Mark mark : tracker.getMarks()) {
    draw(mark.getStartOffset(), mark.getEndOffset(), mark.isPending());
    // إذا isPending() لا تستخدم mark.getOriginal().getQuickFixes() أو getWorkspaceFixes().
}
```

`draw` وبيانات التعديل من تطبيقك. `EditTextSquiggles` يطبق السياسة تلقائياً على الرسم؛ لمحرر آخر يجب رسم المعلّق وتعطيل إصلاحاته في المضيف. حتى للإصلاح الحديث، تحقق من هوية الملف والبصمة قبل التطبيق؛ الإصلاح متعدد الملفات يحتاج transaction للمضيف.

## استخدام أسماء المكتبات المحلولة

بعد أن يحدد المضيف ملفات JAR/AAR **للوحدة والـvariant الحاليين**، وعلى خيط خلفي:

```java
ClasspathSymbols.Result symbols = ClasspathSymbols.scan(resolvedArtifacts);
AnalysisConfig.Builder config = AnalysisConfig.builder()
    .minApi(knownMinSdkOrZero).compileApi(knownCompileSdkOrZero);
symbols.addTo(config);                 // أسماء لمرشحي imports فقط
if (!symbols.isComplete()) reportClasspathScanIncomplete(symbols.getIssues());
Analyzer analyzer = new Analyzer(config.build());
```

المدخل `resolvedArtifacts` هو `List<File>` يوفره المضيف، وليس قائمة يحلها SDK تلقائياً. `isComplete` يخص عملية مسح الأرشيفات المقدمة فقط، ولا يؤكد اكتمال classpath أو رؤية الأنواع. لا يُنفّذ أي bytecode؛ الأصناف المتضاربة تُستبعد، والحدود والملفات التالفة تُبلغ في `getIssues()`. عند تغيير الإصدار أو مجموعة الملفات أعد المسح وابنِ إعداداً جديداً، ولا تفحص الأرشيفات في main thread.

## التحقق الذي أُجري

- `scripts/test-host.sh`: **561 فحصاً** على Linux x86_64 بمحللي JNI الحقيقيين وبدائل واجهة؛ شملت الأسباب المتزامنة وأولوية الخطأ تحت ضغط التحذيرات، وإصلاحاً قديماً، وحذف مورد، وملف مصدر مع syntax مكسور، وإلغاء تحليل XML وإعادة استخدام المحرك، وأرشيفي JAR/AAR واختلاف المحتوى والفساد والتكرار.
- تجربة إعادة استخدام XML: 70 تحليل XML في اللقطة الأولى، و0 في اللقطة المتطابقة، و1 بعد تغيير XML واحد مع إعادة استخدام 69؛ قورنت النتائج بمحرك جديد. هذه **أعداد عمليات** وليست قياس زمن أو أداء Android.
- `scripts/test-sh129-integration.sh`: **20 فحص ربط مع JNI و20 بدونه**، و**60 فحص جودة**، و**15 فحص دورة اعتماديات**، و**24 فحص نقل**، و**25 فحصاً للمحلل القديم**، و3 فحوص نشر و16 فحص تركيب مصدر Java باستخدام JNI وبدائل Android. الاختبار يفحص 70 و405 XML وManifest ومورداً ثنائياً، وتعديل خطأ واستمراره حتى إعادة الفحص، وبصمة إصلاح قديم وإبطال جيل قديم. فحص التركيب بالمحلل ليس ترجمة Android. لم تُشغّل مجموعة QA الكاملة للتطبيق.
- `scripts/check-api21.sh` و`scripts/test-generated-fixes.sh`: جُمعت مصادر SDK وإصلاحات Java نموذجية ضد stubs API 21 خارجية؛ لا تثبت تشغيل الجهاز.
- لم يكتمل بناء AAR/APK، ولم يُختبر المحاكي أو الهاتف أو R8 أو كامل variants؛ لا توجد قياسات سرعة/ذاكرة أو مقارنة تشغيلية مع AIDE. يلزم بناء التطبيق وتثبيته ثم تجربة الحالات وقياسها على مشاريعك وأجهزتك.
